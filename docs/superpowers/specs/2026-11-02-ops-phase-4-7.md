# Operations phase 4–7 design

## Intent
Finish the next operational layer after the original 7-point roadmap: safer install/update UX, broader server administration, lightweight monitoring history, and a profile model that scales to more games without duplicating UI/backend rules.

## Constraints
- Work only in `Nereziel/GameServerControl`.
- Preserve the Agent as source of truth and keep Cloudflare using the same Web UI/API.
- Do not introduce a database or a second dashboard.
- Do not widen filesystem or secret exposure.
- Keep old server definitions and game profiles source-compatible.
- No automatic production deployment or GitHub Release.

## Approaches considered
1. **Large framework rewrite** — split Program.cs, replace profile records with plugins, add a database and generalized command engine. Rejected: too much migration risk for this phase.
2. **Incremental service + metadata extensions** — add focused services/endpoints and extend existing profile metadata while retaining current records and UI. Chosen: lowest compatibility risk and each piece can be CI-gated independently.
3. **UI-only polish** — cheapest, but would leave update rollback, monitoring history and profile duplication unresolved. Rejected.

## Point 4 — install/update UX
Add an Agent update preflight/status API and surface it in global Settings. The preflight reports platform support, update helper presence, current/latest version and whether self-update can start. Harden Windows/Linux installers by staging the previous Agent payload and rolling it back if the new service does not become healthy. Preserve configuration/state files exactly as today.

## Point 5 — server management polish
Keep game-specific command translation in `IGameRcon`, but expose a capability-aware admin surface: list supported standard commands, broadcast/save/shutdown where the handler supports them, and use the existing player list for kick/ban. Do not add raw command support to games without an existing RCON handler. The workspace should render only actions advertised by the backend/profile.

## Point 6 — monitoring/health
Extend the existing in-memory `StatusTracker` with a bounded per-server history of status samples and lifecycle events. Persist no high-frequency metrics to disk. Expose recent history through API and render it in the server Overview/Stats area using simple browser-native bars/sparklines, with bounded retention so memory cannot grow without limit.

## Point 7 — scalable game profiles
Keep `GameProfile` as the public contract but move repeated operational metadata into structured fields: admin command capabilities, config-file roots and platform overrides. Add profile validation so duplicate keys/app IDs, invalid ports and contradictory capabilities fail CI. Existing profile lookup and API shape remain compatible; the new metadata eliminates hard-coded game switches in new work.

## Non-goals
- No new external services.
- No release publication.
- No active testing against production game servers or Cloudflare.
- No migration to a database.
- No generic arbitrary command/file execution API.
